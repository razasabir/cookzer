Cookzer Master Plan

A social network for cooks — Facebook and LinkedIn, vertical to cooking. This is the single reference for what Cookzer is, what's shipped, what's decided, and what's next. Every phase and idea here traces back to an actual conversation and decision, not a guess.

Positioning: home cooks to industry pros
Monetization: none yet — growth first
Infra budget: up to ~$25/mo
Stack: static HTML + Supabase + Vercel
Foundation

Vision & positioning

The reframe that changes priority order: Cookzer is not a recipe app with a social layer bolted on. It's a social network for cooks, the same category shape as Facebook or LinkedIn, just vertical to cooking. Identity, connections, and communication between users are core infrastructure — not features to add once the "real" product exists.

Target users Decided

Spans three groups at once: everyday home cooks (share/get inspiration), aspiring & semi-pro cooks (building a following, small food businesses), and professional chefs/industry (the "LinkedIn for cooking" half — networking, reputation, eventually jobs).

Why mobile-responsive shipped first

Nothing else matters if the site is unusable on a phone. Verified with Playwright at 390px width before any feature work continued.

Foundation

Decisions log

Every real call made so far, with the reasoning — so nothing gets re-litigated later.

Backend: Supabase Shipped

Postgres + built-in Auth + Realtime, on a free tier that fits the ~$25/mo ceiling as it grows. Chosen over Firebase because the relational model + Row Level Security fit user-scoped data (messages, posts, blocks) cleanly, and it integrates natively with Vercel.

Auth methods Shipped (partial)

Email/password shipped and live. Google OAuth deliberately deferred — needs a separate Google Cloud OAuth client the user hasn't set up yet. Ships as a fast-follow once that credential exists.

Auth scope: whole site, not just Messenger Shipped

Every page redirects to sign-in if there's no session — a bigger, deliberate call over gating only Messenger, made once real accounts existed.

Client credentials: publishable key committed to the repo Shipped

Safe by design — Supabase's publishable/anon key is meant to be public, protected by RLS policies, not secrecy. Avoids needing a build step just to inject env vars into static HTML.

Moderation: basic block/report from day one Decided, not yet built

Agreed before launch, not an afterthought — even before there's staffing behind it. Not yet implemented; tracked in the backlog.

Logo & theme: Fredoka, lighter Italian green/red Shipped

Six directions explored; Option 3 (bold two-tone wordmark) won, rendered in Fredoka. Palette shifted from an initial deep forest/rosso to a lighter Italian-flag-inspired green (#009246) and red (#CE2B37) — see Technical reference for full tokens.

Profile reputation: raw stats, not a single rating Decided, not yet built

Rejected a single composite "rating" score — invites gaming and feels judgmental for a community meant to be warm, not purely competitive. Instead: recipes shared, challenges won, times remade, cook-in streak, shown like a game profile card.

No fake profiles or bots to simulate traffic Decided

Rejected outright — presenting fabricated activity as real people is deceptive and carries real trust/legal risk. Honest alternative: seed with real accounts (founder + beta testers) or a clearly labeled "sample content" state.

Progress

Placeholder audit — every page, page by page

A line-by-line pass over all 8 pages to find exactly what's still hardcoded markup pretending to be a product. Each item names the specific button/section that doesn't work today and which phase above already covers the backend it needs — nothing here is a new phase, it's the detail underneath the ones that already exist.

Feed (cookzer-feed.html)

Composer "Photo / Recipe / Challenge" buttons— all three render but have no click handler at all; there is currently no way to actually create a post. Needs the posts table (Phase 1) plus, for the Recipe button, a way to attach an existing or new recipe (Phase 2).
Composer avatar shows hardcoded "RZ"— every other page's avatar is wired by auth-guard.js to the real logged-in user's initials; the feed composer never got that treatment. Small fix, ship with Phase 1.
3 feed cards (Sarah K. / Amina M. / Josh M.)— fully hardcoded HTML, not rows from a table. Only Sarah K.'s recipe title links anywhere. Replace with a real query against posts joined to profiles, ordered by created_at (Phase 1).
Heart counts and comment counts on feed cards— static numbers baked into the HTML, not live, and nothing is clickable to actually heart or open comments. Needs hearts/comments tables and a toggle handler (Phase 1).
Weekly Challenge banner "Join challenge" button— no onclick, no challenge_entries table to join into. Needs a minimal challenges backend before this does anything (Phase 5, or pulled forward if challenges become a priority sooner).
Leaderboard (top 3, sidebar)— hardcoded names/scores. Once challenge entries are real, this becomes a query ordered by hearts on this week's entries (Phase 3 social graph + Phase 5 challenges).
Top Recipes This Week / Trending Ingredients / Top Contributors widgets— all three ship with demo data today. Once real posts and recipes exist, each becomes a genuine aggregate query (most-hearted recipes this week, most-tagged ingredients, most-active posters) rather than a redesign — same markup, real data (Phase 1 for posts-based aggregates, Phase 2 once recipes/ingredients are structured data).

My Cookbook (cookzer-cookbook.html)

4 folders (Weeknight dinners, Ramadan meals, Kids approved, Restaurant recreations)— static divs, not clickable, and there's no "create folder" UI at all. Needs a cookbook_folders table (user-owned, name + emoji) and a join table linking saved recipes to folders (Phase 2).
"Recently saved" recipe items— hardcoded Chicken Karahi / Lentil salad entries with a hand-written note ("less chilli next time"). Needs a real saved_recipes table (user, recipe, optional personal note) and the thumbnails need to actually link to cookzer-recipe.html?id=… instead of nowhere (Phase 2).
Heart / "⋯" more-menu icons on recipe items— decorative, no click handlers anywhere in the file except the shared toggleSidebar(). Once recipes are real, wire heart to the same hearts table as the feed and "⋯" to move-to-folder / remove-from-cookbook actions (Phase 2).

Meal Planner (cookzer-planner.html)

7-day grid (Mon–Sun) with hardcoded meals— "Chicken Karahi," "Lentil salad," etc. are static text, not tied to any date, user, or real recipe row. Needs a meal_plan_entries table (user, date, recipe_id or free-text, meal slot) (Phase 2, since it depends on real recipes existing to attach).
"+ Add meal" button on empty days— renders on every unplanned day but has no onclick — there is no meal-picker modal to search/select a recipe and assign it to a day. Needs to be built once meal_plan_entries exists (Phase 2).
Populated meal slots don't link anywhere— "Chicken Karahi / from your cookbook" is plain text, not a link to the actual recipe page. Trivial fix once each slot has a real recipe_id (Phase 2).
No shopping-list generation— this is already its own phase (Phase 4) rather than a small gap: it needs every planned meal in the week to resolve to a real recipe's ingredient list, then consolidate quantities across recipes. Blocked on Phase 2 (real recipes) landing first.

Challenges (cookzer-challenges.html)

"Join the challenge" button on the hero card— no onclick, and "214 cooks entered so far" is a hardcoded number. Needs a challenges table (current theme, end date) and a challenge_entries table (user, challenge, recipe/post, hearts) — this is the single biggest gap on this page (Phase 5).
Filter chips (Diet / Cuisine / Cook time / Budget)— "Budget" renders with the active class but none of the four chips have a click handler, and there's nothing to filter yet since entries aren't real. Depends on Recipe categories + Dietary filters shipping on the recipes table first (Phase 2), then wiring the chips to actually filter the leaderboard/entries list (Phase 5).
Leaderboard (5 hardcoded entries)— names, dishes, and heart counts are static; entries don't link to the cook's profile or the actual recipe they made. Becomes a real query against challenge_entries joined to profiles and recipes, ordered by hearts (Phase 3 + Phase 5).

Profile (cookzer-profile.html)

Entire header is hardcoded to one person ("Raza K.")— name, location ("Melbourne, Australia • Joined this year"), and avatar initials "RZ" are static text regardless of who's logged in. This page needs to read the real profiles row for whichever user's profile is being viewed (own profile vs. someone else's — currently there's no concept of viewing anyone else's profile at all) (Phase 3).
"Edit profile" button does nothing— no onclick, no edit form or modal exists anywhere in the codebase. This needs its own build: a form/modal for display name, bio, location, and avatar image, writing back to the profiles table (currently only auto-populated by the signup trigger, never user-editable). Call this out as its own concrete task under Phase 3, not an afterthought of "real profile page."
"Share" button does nothing— no onclick. Needs a copy-to-clipboard profile link at minimum (same pattern as the "Share recipe link" Now-bucket idea, just applied to a profile URL instead of a recipe) (Phase 3, or pull into the Now bucket as a quick client-side win once profile URLs exist).
Stats block (34 Recipes / 512 Followers / 128 Following)— fabricated numbers. This is exactly the "Profile stats" decision already logged above (raw stats, not a rating) — needs real counts: recipes authored, follower/following rows once the social graph exists, challenges won, times remade, cook-in streak (Phase 3).
View tabs (Grid view / List view / Saved)— three tabs render but none have a click handler to actually switch the displayed layout or swap in a different data set for "Saved" vs. "posted." Needs real state-switching logic once there's real post data to switch between (Phase 3).
9 post-cards in the grid— all fully hardcoded (Chicken Karahi, Lentil salad, Brown butter gnocchi, etc.), none have an href or onclick. Needs to become a real query for this user's posts/recipes, each card linking to its recipe page (Phase 2 for recipes existing, Phase 3 for it being "this user's" posts specifically).
4 achievement badges— hardcoded ("🍳 30 recipes cooked," "🔥 5-week streak," etc.), not computed from anything. Once stats are real (above), badges become threshold checks against those same numbers (Phase 3).
No .avatar element in this page's header at all— every other page has a header avatar that auth-guard.js wires up with real initials and a sign-out click handler; this page's header only has 🔔 and 💬 icon buttons. This is a real bug, not just a content gap — sign-out is unreachable from the Profile page today. Quick fix, doesn't need to wait for any phase.

Messenger (cookzer-messenger.html) — mostly real, but gaps remain

No group conversations— schema and UI only support 1:1 threads (conversation_participants supports more than 2 rows already, but nothing in the client creates or renders a 3+ person thread). Needs UI for multi-select on "New Message" and a group name/avatar concept.
No file or image attachments in messages— only plain text messages are supported. Needs Supabase Storage wiring (same gap as the recipe page gallery below) plus a messages.attachment_url column.
No emoji reactions or read receipts surfaced— last_read_at already exists in the schema and is updated on open, but nothing in the UI shows a "Seen" indicator yet; already tracked as Now-bucket items #11–12.

Recipe page (cookzer-recipe.html)

Photo gallery upload is client-side only— the upload + filter picker (7 CSS filter presets) works and appends a new gallery thumbnail, but nothing is persisted to Supabase Storage or a recipe_photos table — refreshing the page loses every uploaded photo. This is the single biggest gap on an otherwise-shipped page (Phase 2, needs Supabase Storage bucket + RLS policy in addition to the recipes table).
Only one real recipe exists (Homemade Chicken Karahi)— every link to a recipe across the whole site (feed, cookbook, planner, challenges, profile) points at this same single hardcoded page. There is no dynamic cookzer-recipe.html?id=… route yet — this is the actual meaning of "Phase 2: dynamic recipe detail page" and it's what unblocks every other page's recipe links above.

Reference

Competitive research

Five real platforms researched for mechanics worth adapting, not copying. Full recommendation: don't compete on recipe-database size or import integrations — that's a war against Cookpad and Samsung Food that can't be won right now. The real gap is that none of the pure recipe apps have Untappd/Letterboxd-style logging, streaks, and identity-through-taste, and Cookzer is already social-first.

Cookpad

World's largest UGC recipe community. Standout: "Cooksnaps" — cook someone's recipe, post your result attached to the original.

→ Remakes: credited, first-class, feeds a leaderboard

TikTok food discovery

37% of people find food via social feeds; algorithms surface live trending dishes, not evergreen categories.

→ Trend Radar: live trends spawn mini-challenges

Untappd

Beer check-ins — a low-friction tap-and-rate, separate from a full review, with streaks and badges.

→ Cook-ins: one-tap "I cooked this," builds a streak

Letterboxd

Film logging — an automatic diary plus curatable public Lists. Identity through taste, not just posts.

→ Cooking Diary + Lists on My Cookbook

Culinary Agents

"LinkedIn for chefs" — a professional network + job board where profiles double as a resume.

→ Kitchen CV mode for industry users

Hard-won lessons

RLS self-reference = infinite recursionA policy that queries its own table inside its own USING clause makes Postgres re-apply that policy to evaluate itself, forever. Fix: a SECURITY DEFINER function that checks membership with RLS bypassed for that one internal lookup.
Insert-then-.select() chicken-and-egg.insert({...}).select() tries to read the new row back immediately — but if the SELECT policy requires state the insert itself is establishing (e.g. "you must already be a participant"), it fails. Fix: generate the ID client-side with crypto.randomUUID() and skip .select() entirely.
Supabase's default email sender is rate-limitedFine for a couple of test signups, not production. Needs a real SMTP provider (Resend, SendGrid, Postmark) before any public launch.
New Supabase key system"Publishable" replaces the old "anon" key, "Secret" replaces "service_role" — same purpose, new names. Only the publishable key belongs in client code.

Cookzer Master Plan

A social network for cooks — Facebook and LinkedIn, vertical to cooking. This is the single reference for what Cookzer is, what's shipped, what's decided, and what's next. Every phase and idea here traces back to an actual conversation and decision, not a guess.

Positioning: home cooks to industry pros
Monetization: none yet — growth first
Infra budget: up to ~$25/mo
Stack: static HTML + Supabase + Vercel
Foundation

Vision & positioning

The reframe that changes priority order: Cookzer is not a recipe app with a social layer bolted on. It's a social network for cooks, the same category shape as Facebook or LinkedIn, just vertical to cooking. Identity, connections, and communication between users are core infrastructure — not features to add once the "real" product exists.

Target users Decided

Spans three groups at once: everyday home cooks (share/get inspiration), aspiring & semi-pro cooks (building a following, small food businesses), and professional chefs/industry (the "LinkedIn for cooking" half — networking, reputation, eventually jobs).

Why mobile-responsive shipped first

Nothing else matters if the site is unusable on a phone. Verified with Playwright at 390px width before any feature work continued.

Foundation

Decisions log

Every real call made so far, with the reasoning — so nothing gets re-litigated later.

Backend: Supabase Shipped

Postgres + built-in Auth + Realtime, on a free tier that fits the ~$25/mo ceiling as it grows. Chosen over Firebase because the relational model + Row Level Security fit user-scoped data (messages, posts, blocks) cleanly, and it integrates natively with Vercel.

Auth methods Shipped (partial)

Email/password shipped and live. Google OAuth deliberately deferred — needs a separate Google Cloud OAuth client the user hasn't set up yet. Ships as a fast-follow once that credential exists.

Auth scope: whole site, not just Messenger Shipped

Every page redirects to sign-in if there's no session — a bigger, deliberate call over gating only Messenger, made once real accounts existed.

Client credentials: publishable key committed to the repo Shipped

Safe by design — Supabase's publishable/anon key is meant to be public, protected by RLS policies, not secrecy. Avoids needing a build step just to inject env vars into static HTML.

Moderation: basic block/report from day one Decided, not yet built

Agreed before launch, not an afterthought — even before there's staffing behind it. Not yet implemented; tracked in the backlog.

Logo & theme: Fredoka, lighter Italian green/red Shipped

Six directions explored; Option 3 (bold two-tone wordmark) won, rendered in Fredoka. Palette shifted from an initial deep forest/rosso to a lighter Italian-flag-inspired green (#009246) and red (#CE2B37) — see Technical reference for full tokens.

Profile reputation: raw stats, not a single rating Decided, not yet built

Rejected a single composite "rating" score — invites gaming and feels judgmental for a community meant to be warm, not purely competitive. Instead: recipes shared, challenges won, times remade, cook-in streak, shown like a game profile card.

No fake profiles or bots to simulate traffic Decided

Rejected outright — presenting fabricated activity as real people is deceptive and carries real trust/legal risk. Honest alternative: seed with real accounts (founder + beta testers) or a clearly labeled "sample content" state.

Test infrastructure: checked-in Playwright, not forever-throwaway Shipped

First asked, chose "keep it lightweight, no new deps" and kept using scratch verification scripts per feature. Revisited once it was clear scratch scripts were being rebuilt from scratch every time — package.json + Playwright cost nothing (open-source, no network calls, fits GitHub Actions' free tier) and the site stays a zero-build static site otherwise; only the test suite gained a build step.

Restaurant ratings require a receipt photo Shipped

A rating can't be submitted without attaching a receipt or invoice photo as proof of the visit — a deliberate friction cost to keep ratings honest, over allowing frictionless star ratings that are easy to fake.

Investor pitch page lives off the main nav, at /nadir Shipped

A separate route rather than a page reachable from the app shell — it's a pitch artifact for a specific audience, not part of the product a cook would use.

Co-Cooks: a sidebar widget, not a nav page Shipped

First shipped as a full page with its own nav link, matching Groups/Restaurants — reworked after user feedback into a compact "up to 7 avatars + settings" widget pinned to the bottom of the sidebar on every page, since friends are meant to be glanceable, not a destination.

Reference

Competitive research

Five real platforms researched for mechanics worth adapting, not copying. Full recommendation: don't compete on recipe-database size or import integrations — that's a war against Cookpad and Samsung Food that can't be won right now. The real gap is that none of the pure recipe apps have Untappd/Letterboxd-style logging, streaks, and identity-through-taste, and Cookzer is already social-first.

Cookpad

World's largest UGC recipe community. Standout: "Cooksnaps" — cook someone's recipe, post your result attached to the original.

→ Remakes: credited, first-class, feeds a leaderboard

TikTok food discovery

37% of people find food via social feeds; algorithms surface live trending dishes, not evergreen categories.

→ Trend Radar: live trends spawn mini-challenges

Untappd

Beer check-ins — a low-friction tap-and-rate, separate from a full review, with streaks and badges.

→ Cook-ins: one-tap "I cooked this," builds a streak

Letterboxd

Film logging — an automatic diary plus curatable public Lists. Identity through taste, not just posts.

→ Cooking Diary + Lists on My Cookbook

Culinary Agents

"LinkedIn for chefs" — a professional network + job board where profiles double as a resume.

→ Kitchen CV mode for industry users

Hard-won lessons

RLS self-reference = infinite recursionA policy that queries its own table inside its own USING clause makes Postgres re-apply that policy to evaluate itself, forever. Fix: a SECURITY DEFINER function that checks membership with RLS bypassed for that one internal lookup.
Insert-then-.select() chicken-and-egg.insert({...}).select() tries to read the new row back immediately — but if the SELECT policy requires state the insert itself is establishing (e.g. "you must already be a participant"), it fails. Fix: generate the ID client-side with crypto.randomUUID() and skip .select() entirely.
Supabase's default email sender is rate-limitedFine for a couple of test signups, not production. Needs a real SMTP provider (Resend, SendGrid, Postmark) before any public launch.
New Supabase key system"Publishable" replaces the old "anon" key, "Secret" replaces "service_role" — same purpose, new names. Only the publishable key belongs in client code.
Ambiguous embeds (PGRST201) when a table has two paths to the same targetchallenge_entries has direct foreign keys to posts, recipes, and profiles all at once, so any query embedding e.g. profiles(...) straight off posts has two valid join paths and PostgREST refuses to guess. Fix: name the exact constraint, e.g. profiles!posts_author_id_fkey(...).
The browser's disk cache can mask a successful writeA freshly-inserted row can fail to show up on reload because the browser served the follow-up GET from cache instead of the network — looks exactly like the write silently failed. Fix: pass a custom fetch into createClient() that forces cache: 'no-store'.

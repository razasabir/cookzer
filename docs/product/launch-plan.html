Architecture review

  • The gap is systemic, not two isolated incidents

    Two for two so far: migration 029 (group management, found and repaired earlier) and migration 024 (Tip posts, found and repaired today) were both bootstrap-assumed "already applied by hand" in scripts/apply-migrations.sh and both turned out not to be. That script's tracking table (public._schema_migrations) only marks a migration done when the runner itself applies it — anything before migration 030 rests entirely on a one-time assumption made when the pipeline was first built, and that assumption has now failed verification twice. Every feature built on migrations 017-029 should be treated as unverified on production, not confirmed, until checked individually or a defensive repair is written for it (the pattern from 034 and 037: drop ... if exists / add column if not exists / create ... if not exists, safe to run regardless of current state).

    Systemic risk

  • Why CI passing doesn't rule this class of bug out

    The Playwright suite mocks window.supabase entirely, so a client that sends the exact right payload (as the Tip composer did) still shows green even when the live database would reject that same payload. The deploy pipeline's own migration-apply step is real evidence, though — it's now been checked directly for migrations 035-037 (this session's own additions) via GitHub Actions job logs, and all applied cleanly. The gap is specifically in the pre-030 range the pipeline never actually verified, not in anything shipped since.

    Confirmed

  • Everything checked this round is correctly wired end to end

    Family Profiles ↔ Meal Planner columns ↔ household size, the friend-linking picker, and the migration-driven RLS policies behind all of it (owner_id/group_id sharing on meal_suggestions) all trace cleanly from client call → RLS policy → table, with no other dangling references found. The only structural issue this round was the pre-030 migration-application gap above, not a design or wiring problem.

    Confirmed
